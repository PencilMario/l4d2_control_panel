# 游戏实例控制台缓存上限设计

## 目标

将游戏实例控制台在关闭并重新打开后可恢复的历史缓存，以及浏览器当前显示缓存的上限统一调整为最多 8192 行。

## 基线事实

- 当前分支的后端 `internal/httpapi/console.go` 使用 `maxConsoleHistoryLines = 1000`。
- 当前分支的前端 `web/src/app/consoleBuffer.ts` 使用 `NATIVE_CONSOLE_MAX_LINES = 1000`。
- 后端还存在 `maxConsoleHistoryBytes = 1 << 20` 的字节上限；本次保留该安全边界。
- 用户提出的旧值为 512 行，但当前分支实际代码为 1000 行；本次以目标值 8192 行和当前代码为准。

## 方案与取舍

1. **推荐：同步调整两层行数上限，保留后端 1 MiB 字节上限。**
   修改两个已有常量，确保后端重新订阅时提供更多历史，前端也不会再次提前截断。实现面最小；超长单行输出仍可能使后端实际保留少于 8192 行。
2. 同步调整行数上限并将后端字节上限同步扩大到约 8 MiB。
   可减少长行导致的行数折损，但会扩大每个实例的进程内内存上界，且超出本次明确的“行数”需求。
3. 只调整后端或只调整前端。
   会让另一层继续成为 1000 行瓶颈，不满足用户看到和重开控制台都能保留更长历史的目标。

本次采用方案 1。

## 范围与兼容性

- 修改后端控制台会话历史和前端控制台输出的行数常量。
- 保持已认证的 WebSocket 地址、文本/二进制命令输入、实例隔离、实时输出、字节上限和进程内历史生命周期不变。
- 不新增配置项，不改变持久化，不扩大到游戏日志、性能历史或其他缓存。

## 验收标准

- 后端跨帧追加 8193 行时仅保留最新 8192 行。
- 前端使用默认参数追加 8193 行时仅保留最新 8192 行。
- 既有控制台相关 Go 测试和前端单元测试通过；前端生产构建通过。
- 工作区原有的其他用户改动不被修改。
