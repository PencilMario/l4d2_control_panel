# 插件包来源与实例完整更新设计

状态：已批准  
日期：2026-07-29

## 1. 目标

重新建立插件包仓库与游戏实例之间的稳定边界：插件包分为常规插件包和 GitHub 源插件包；内容仓库负责取得内容，游戏实例负责部署内容。实例插件更新只保留完整更新一种语义。

修复以下主路径：GitHub 发布新版本后，管理员可以先在内容仓库同步源再更新实例，也可以直接更新实例；两条路径最终都必须把该源的最新 Release 完整部署到目标实例。

## 2. 根因与现状

当前实现同时使用 `SelectedPackageID`、`PackageSourceRepository` 和 `PackageVersion` 表示插件状态，但没有严格区分稳定来源和具体版本：

- GitHub 源同步只下载新包，不部署实例，这是正确边界，但界面和状态未清晰表达。
- 部分部署路径按 GitHub 仓库解析最新包，部分路径仍传入此前解析的具体包 ID。
- 包部署成功后，协调器会把 `SelectedPackageID` 改为已部署包 ID，使来源选择和版本状态继续耦合。
- 热更新、完整更新、固定包重装和 Release 更新由多条协调路径持有，测试没有覆盖“新 Release 到实例部署”的完整链路。

因此当前测试虽然通过，仍不能证明源同步后的实例会部署新版本。

## 3. 领域模型

### 3.1 插件选择

实例的插件选择只有两种，且必须互斥：

- **常规插件包**：由固定 `package_id` 标识。它是不可更新的内容快照。
- **GitHub 源插件包**：由稳定 `source_id` 标识。源包含仓库和 Release 资源匹配规则，可解析出当前最新的具体包。

不得再使用仓库字符串作为实例的规范外键，也不得用某次 GitHub Release 的包 ID 表示实例选择的 GitHub 源。

### 3.2 已部署版本

`applied_package_id` 只表示实例最后一次成功部署的具体包 ID：

- 常规包成功部署后，它等于所选 `package_id`。
- GitHub 源包成功部署后，它等于当次解析和部署的 Release 包 ID。
- 同步、下载、部署或恢复失败时不得提前修改。

### 3.3 更新语义

插件更新只保留**实例完整更新**：停止活动实例、事务化部署完整插件包、重放实例私有文件、恢复最新期望状态。

删除热更新作为领域概念：插件包不再声明热更新兼容性，实例和内容仓库不再展示热更新/完整更新选择，API 和计划任务不再产生新的热更新模式。

## 4. 操作流程

### 4.1 内容仓库同步 GitHub 源

内容仓库的“同步”操作只执行：

1. 查询 GitHub 最新 Release。
2. 按资源规则选择归档。
3. 若仓库中尚无该版本，则下载、检查并登记具体包。
4. 返回是否发现新版本以及当前最新包信息。

该操作不选择实例、不停止实例、不部署实例。常规包没有同步或检查更新操作。

### 4.2 更新实例插件

实例更新在持久 Job 中串行执行：

1. 重新读取实例的最新插件选择和期望状态。
2. 常规包通过 `package_id` 取得固定包；GitHub 源通过 `source_id` 读取源配置，并先同步最新 Release。
3. 解析出本次具体包后，停止活动实例。
4. 使用现有事务流水线执行完整部署并重放私有文件。
5. 按实例最新期望状态恢复运行或保持停止。
6. 事务提交成功后写入 `applied_package_id`。

GitHub 没有新 Release 时仍完整重装仓库中的当前最新版本。源同步失败、包不存在或部署失败时 Job 失败，并保留原 `applied_package_id`。

## 5. API 与界面

- 实例配置写入固定 `package_id` 或 GitHub `source_id`，不得同时提交。
- 实例响应继续暴露 `applied_package_id`，并明确暴露当前选择类型和对应引用。
- 实例卡片只提供“更新插件”命令，确认信息说明将完整重装。
- 内容仓库分别展示常规包和 GitHub 源；GitHub 源提供“同步”，常规包不显示更新能力。
- 旧的 `mode: hot` 不再被新 API 接受；插件部署入口不要求客户端传更新模式。
- 后台任务与日志应区分“同步 GitHub 源”和“完整更新实例插件”。

## 6. 迁移与兼容边界

- 为实例增加规范 `source_id` 外键；已有 `package_source_repository` 根据现存 GitHub 源仓库匹配并迁移。
- 无法唯一匹配来源的旧实例不得静默猜测，应保留可诊断迁移状态或明确报错。
- 普通实例继续保留固定 `package_id`；已有 `applied_package_id` 原样保留。
- 旧 `package_hot` 计划任务迁移为固定包完整更新，旧 `release_hot` 迁移为 GitHub 源同步后完整更新。
- 新建计划任务不再提供 `package_hot`、`release_hot`；现有完整更新任务收敛到统一实例更新协调器。
- 旧仓库字符串字段只在迁移/读取兼容期存在，不继续作为规范写入路径。
- 保留现有部署事务、回滚、私有文件优先级、实例 Job 串行化和期望状态语义。

## 7. 错误处理

- GitHub API、资源匹配、下载或归档校验失败：不停止实例，不改变已部署版本。
- 停止实例失败：不开始部署。
- 部署或私有文件重放失败：按现有事务规则回滚，不改变已部署版本。
- 恢复启动或健康检查失败：执行既有回滚/故障状态策略，Job 明确记录失败阶段。
- 删除仍被实例选择或引用为已部署版本的源、包时必须拒绝，或使用已有安全保留策略；不得制造悬空引用。

## 8. 测试与验收

自动化测试至少覆盖：

- 常规包完整重装且不会访问 GitHub。
- GitHub 实例更新自动同步新 Release 并部署新包。
- 内容仓库先同步后，实例更新部署已同步的最新版。
- GitHub 无新 Release 时完整重装当前最新版。
- 内容仓库同步不会部署或改变任何实例。
- 同步和部署各阶段失败时保持原插件选择与 `applied_package_id`。
- 实例只能选择固定包或 GitHub 源之一。
- 旧实例字段以及 `package_hot`、`release_hot` 任务正确迁移。
- 前端不再显示或提交热更新模式。

主验收路径：创建 GitHub 源并绑定实例，部署版本 A；发布版本 B 后分别验证“直接更新实例”和“先同步源再更新实例”两条路径，最终实例的 `applied_package_id` 均指向 B，实例来源仍指向同一个 `source_id`。

## 9. 非目标

- 不在源同步完成后自动批量部署所有绑定实例。
- 不让一个实例同时叠加多个插件包或多个 GitHub 源。
- 不实现 Release 回退、版本锁定或自动清理历史包策略。
- 不改变共享游戏本体更新语义。

## 10. 工作草案摘要

`TaskIntentDraft`：把插件包来源与已部署版本分离，修复 GitHub 新 Release 无法经实例更新部署的问题，并删除热更新分支。

`BaselineReadSetHint`：设计受 `CONTEXT.md`、实例启动插件选择设计、实例选择性重装设计、`internal/content`、`internal/releases`、`internal/updates`、`internal/httpapi`、持久化迁移和 React 内容仓库/实例界面约束。

`ImpactStatementDraft`：变更跨越实例模型、存储迁移、GitHub 同步、更新协调、计划任务、API 和前端。规范所有者是实例的稳定插件选择；具体包只作为仓库版本和成功部署结果。兼容边界是保留事务回滚、私有层、Job 串行和实例期望状态。
